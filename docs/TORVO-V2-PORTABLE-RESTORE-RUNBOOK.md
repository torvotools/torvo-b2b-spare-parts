# TORVO V2 PORTABLE RESTORE & ACCEPTANCE RUNBOOK

Status: canonical handover procedure. This document does not prove that a restore rehearsal has been executed.

## Purpose
Restore TORVO V2 into a clean target environment without creating a second production system or silently changing business/security rules.

## Non-negotiable boundaries
- Production project `gckafjiitjocodlrwanm` must not be used for a rehearsal.
- Rehearsals use an isolated staging/restore target only.
- Source branch is `torvo-v2-build`; V27/main is reference-only.
- Restore exactly one authoritative database/backend.
- Never copy service-role keys, OTP/provider secrets, signing keys, passwords, or other secrets into source control or a backup artifact.
- Preserve LOCKed UI unless the Owner explicitly unlocks it.
- Retired public retail pricing/checkout migrations must never be enabled.

## Restore package must contain
1. Database backup artifact.
2. SHA-256 checksum and artifact size.
3. Database/schema version.
4. Exact Git commit SHA and branch.
5. Restore manifest generated by the trusted backup worker.
6. Migration/install-order reference: `supabase/V2_INSTALL_ORDER.md`.
7. Environment-variable NAME inventory only; secret VALUES stay outside the package.
8. Release metadata needed to identify the matching web/app build.

A package is not a verified restore point unless its checksum, commit, schema/database versions and manifest agree with the recorded backup metadata.

## Clean-target restore sequence
1. Create/select an isolated restore target; confirm it is not production.
2. Record target project/environment identifiers before any write.
3. Verify backup SHA-256 and file size before restore.
4. Check out the exact `torvo-v2-build` commit recorded in the manifest.
5. Restore the database artifact into the clean target.
6. Follow `supabase/V2_INSTALL_ORDER.md` only for migrations/functions not already represented by the restored artifact. Do not replay migrations blindly.
7. Configure runtime secrets through the target platform secret store; never import secret values from Git/source artifacts.
8. Deploy required Edge Functions and application build from the same recorded commit.
9. Keep the target isolated from the production domain and production outbound integrations until acceptance passes.

## Mandatory acceptance gates
### Database/security
- Expected migrations are present in dependency order.
- All exposed public tables have intended RLS.
- Sensitive PIN/OTP/session/payment/profit/purchase/return/backup/release functions are not anonymously executable unless explicitly documented as public runtime endpoints.
- Dealer/staff authorization derives identity server-side.

### Authentication
- Real authorized staging Dealer login/session/logout/revoke flow passes.
- Real authorized staging Staff master-email OTP/session/revoke flow passes.
- Blocked/inactive and wrong-session cases are rejected.

### Business workflow
Using approved staging test records, verify:
Dealer order -> Sales Order -> Dealer OK -> Estimate -> Payment/Fulfilment -> Dispatch -> Delivery.
Also verify Purchase -> Stock receipt, Sales Return, Purchase Return, inventory movements and idempotency/concurrency protections.

### Reports
Verify summary/detail values against the same known staging transactions. The authoritative summary definition is `v2-report-summary-rpc.sql`; do not overwrite it with the older overlapping reporting definition.

### Backup/restore evidence
Record:
- source backup_run id
- restore manifest id
- source commit SHA
- target environment/project id
- checksum verification result
- restore start/end timestamps
- acceptance tester
- PASS/FAIL for each gate
- defects and fixes
- final rehearsal verdict

### App/release
For Android production acceptance, verify the published artifact is HTTPS, SHA-256 matched, production-signed, package `com.torvotools.app`, approved production channel, and tied to the accepted commit. Perform real-device install/update/login checks before calling the APK accepted.

## Failure rule
Any checksum mismatch, wrong commit, missing migration, authorization leak, failed business invariant, report mismatch, or app-signature/package mismatch is a FAIL. Fix the root cause and repeat the affected gate; never mark it PASS by documentation alone.

## Production cutover rule
A successful staging restore rehearsal is evidence for portability, not permission to alter production. Production/domain cutover is a separate explicit acceptance step. V27 remains untouched until TORVO V2 production acceptance, required backup/reference preservation, and explicit cleanup stage are complete.


## Executable pre-restore artifact verification
Before any clean-target restore, run the repository verifier against the trusted-worker manifest export and the exact backup artifact:

`npm run verify:v2-backup-artifact -- <manifest.json> <artifact>`

The verifier checks the real artifact bytes against SHA-256, requires branch `torvo-v2-build`, an exact 40-character code commit, encrypted=true and includes_secrets=false. A PASS here proves artifact/manifest integrity only. It does **not** prove that a restore rehearsal, authentication test, business reconciliation, or production acceptance has passed.
